3//! Page-cache infrastructure shared by filesystems, memory mappings, and
4//! writeback.
5//!
6//! This module is the filesystem-facing entry point to the page-cache
7//! subsystem. A filesystem typically keeps one [`PageCache`] per file (or per
8//! inode data stream) and uses it for buffered I/O, truncate/extend, and cache
9//! invalidation.
10//!
11//! # Overview
12//!
13//! The subsystem is split into four layers with different responsibilities:
14//!
15//! - [`PageCache`] is the per-file façade used by filesystems. It exposes
16//!   buffered I/O, resize, flush, and invalidation operations in filesystem
17//!   terms.
18//! - [`Vmo`] is the lower-level memory object underneath a page cache. It owns
19//!   the page array, commits pages on demand, and is the abstraction shared
20//!   with page-fault and mapping code.
21//! - [`CachePage`] stores cached page contents, while
22//!   [`cache_page::PageState`] records whether those contents are uninitialized,
23//!   clean, or dirty.
24//! - [`PageCacheBackend`] is the storage-facing contract used
25//!   to make a page readable or durable. [`BlockAsPageCacheBackend`] is a
26//!   helper interface for backends that can satisfy that contract with
27//!   block-device BIOs.
28//!
29//! For a file with a backend, the steady-state flow is
30//! `filesystem metadata -> PageCache -> Vmo -> PageCacheBackend -> block
31//! device or remote server`. Anonymous page caches use the same `PageCache` / `Vmo` layers
32//! without a backend.
33//!
34//! # Responsibility Boundary
35//!
36//! `PageCache` manages page-aligned cache capacity and cached contents. The
37//! filesystem still owns file size, extent or block mapping metadata, and the
38//! higher-level locking that keeps those decisions stable while the page cache
39//! is accessed.
40//!
41//! Stay at [`PageCache`] when the caller is operating in filesystem terms. Drop
42//! to [`Vmo`] only when code needs the lower-level memory-object interface
43//! directly, such as `mmap` setup or page-fault handling.
44//!
45//! # Synchronization Model
46//!
47//! The page-cache subsystem serializes per-page state transitions, including
48//! the backend page states in [`cache_page::PageState`] and the auxiliary
49//! writeback tracking bit in [`CachePageMeta`].
50//!
51//! [`PageCache`] is stored inside a filesystem-level lock or inode lock. It
52//! prevents conflicting buffered I/O and resizing. However, it cannot prevent
53//! concurrent page faults. They need to be synchronized with page table locks,
54//! the reverse-mapping lock, and per-page locks. This module handles the
55//! complexity in cooperation with [`super::vmar`].
56//!
57//! A complete overview of how cached file I/O ("read"/"write" below),
58//! `O_DIRECT` file I/O ("read (direct)"/"write (direct)"), page cache
59//! management operations ("resize"/"flush"/"evict"), and page faults
60//! ("fault (load)"/"fault (store)") interact with each other when they are
61//! invoked concurrently is shown below.
62//!
63//! |                | read            | write           | read (direct) | write (direct)  | resize      | flush       | evict       | fault (load) | fault (store) |
64//! |----------------|-----------------|-----------------|---------------|-----------------|-------------|-------------|-------------|--------------|---------------|
65//! | read           | N/A             |                 |               |                 |             |             |             |              |               |
66//! | write          | inode*          | inode*          |               |                 |             |             |             |              |               |
67//! | read (direct)  | N/A             | (flush)         | N/A           |                 |             |             |             |              |               |
68//! | write (direct) | (flush + evict) | (flush + evict) | inode*        | inode*          |             |             |             |              |               |
69//! | resize         | inode           | inode           | inode         | inode           | inode       |             |             |              |               |
70//! | flush          | N/A             | page            | (flush)       | (flush + evict) | rmap + page | rmap + page |             |              |               |
71//! | evict          | N/A             | page            | (flush)       | (flush + evict) | rmap + page | rmap + page | rmap + page |              |               |
72//! | fault (load)   | N/A             | N/A             | N/A           | (flush + evict) | PT + xarray | N/A         | PT + page   | N/A          |               |
73//! | fault (store)  | N/A             | N/A             | (flush)       | (flush + evict) | PT + xarray | PT + page   | PT + page   | N/A          | N/A           |
74//!
75//! The annotations in the table are explained below.
76//!
77//!  - If two operations have no semantic conflicts, even if they are called
78//!    concurrently (e.g., if both operations try to read something), the
79//!    corresponding entry is noted as `N/A`.
80//!
81//!  - Userspace programs should not mix cached and direct file I/O. Otherwise,
82//!    data corruption caused by the program will be the user's fault. The
83//!    corresponding entry is noted as `(OP)` where `OP` is the operation
84//!    inserted by the filesystem before starting direct file I/O, which
85//!    ensures the correctness when the two operations are called
86//!    **sequentially**.
87//!
88//!  - For two operations protected by the inode lock, the entry is noted as
89//!    `inode` or `inode*`. The latter, `inode*`, means that lock usage is not
90//!    yet enforced at the page cache layer or the Rust type level (i.e.,
91//!    [`PageCache`] operations do not yet take `&mut self`).
92//!
93//!  - In this table, `flush` and `evict` are assumed to be able to be called
94//!    without holding the inode lock (e.g., under memory pressure). But as we
95//!    have not implemented any related mechanisms, they can currently only be
96//!    called from the filesystem while holding at least the inode read lock.
97//!
98//!  - For interactions between page faults and page cache management, the
99//!    correct order of multiple locks is important to ensure that the cached
100//!    page is always in a consistent state, even when operations are called
101//!    concurrently. The corresponding entry is noted as `LockA + LockB`. We
102//!    use `rmap` to denote the reverse-mapping lock, `PT` to denote the page
103//!    table lock, `page` to denote the page lock, and `xarray` to denote the
104//!    lock of VMO pages. For details, see the comments in the implementation.

126/// The page cache for a file-like object.
127///
128/// This is the abstraction a filesystem usually stores in an inode: it handles
129/// buffered reads and writes, writeback, invalidation, and page-cache resizing,
130/// while delegating per-page population and writeback to the underlying [`Vmo`].
131///
132/// A `PageCache` owns cached page contents and a page-aligned capacity. It does
133/// not own:
134///
135/// - the filesystem's file size (EOF);
136/// - extent or block-mapping metadata; or
137/// - the higher-level synchronization that keeps metadata, buffered I/O,
138///   invalidation, and VM mappings coherent.
139///
140/// Filesystems backed by persistent or remote storage create it with
141/// [`PageCache::new_with_backend`] and a [`PageCacheBackend`]. Purely
142/// in-memory filesystems can use [`PageCache::new_anon`] to get the same
143/// buffered-I/O interface without a backend.
144///
145/// A `PageCache` is more than just an `Arc<Vmo>` wrapper. It acts as a unique
146/// handle to the underlying [`Vmo`], enabling additional operations and
147/// enforcing the correct concurrency contract (see the module-level
148/// documentation of [`crate::vm::page_cache`]). Typically, a user (such as a
149/// file system) should place a `PageCache` inside a [`Mutex`] or [`RwMutex`].
150/// Operations requiring exclusive access to the page cache handle require
151/// `&mut self`, so a proper inode or file system lock must be obtained in
152/// advance.
153///
154/// Reach for [`PageCache::as_vmo`] only when a lower-level consumer such as
155/// memory mapping or page-fault code must operate on the underlying [`Vmo`]
156/// directly.
157#[derive(Debug)]
158pub(crate) struct PageCache(Arc<Vmo>);

181    /// Returns the current page-cache capacity in bytes.
182    ///
183    /// This size is page-aligned and may exceed the file size. The filesystem
184    /// remains responsible for tracking EOF separately.
185    pub(crate) fn size(&self) -> usize {
186        self.0.size()
187    }

189    /// Resizes the page-cache capacity to cover a new file size.
190    ///
191    /// `new_file_size` is the post-resize file size requested by the filesystem.
192    /// The underlying cache capacity is rounded up to page boundaries. If the
193    /// new size is smaller than the current size, pages that fall entirely
194    /// within the truncated range will be decommitted (freed). For the page
195    /// that is only partially truncated (i.e., the page containing the new
196    /// boundary), the truncated portion will be filled with zeros instead.
197    ///
198    /// The `old_file_size` must be the file length before this resize. It is
199    /// used to determine the boundary of previously valid data so that only the
200    /// discarded range within a partially truncated tail page is zero-filled.
201    ///
202    /// Extending the page cache does not eagerly allocate pages and therefore
203    /// cannot return an error. Shrinking may fail because it can zero-fill or
204    /// decommit existing pages.
205    ///
206    /// # Size Synchronization
207    ///
208    /// `PageCache::resize` only updates the page-aligned [`Vmo`] capacity. The
209    /// filesystem must keep that capacity synchronized with its own file size
210    /// under the same inode- or file-level lock that excludes conflicting
211    /// buffered I/O and resizing.
212    ///
213    /// The required ordering is:
214    ///
215    /// - When extending a file, update the file size before increasing
216    ///   [`Vmo::size`] so subsequent reads can observe the new range.
217    /// - When truncating a file, shrink [`Vmo::size`] before decreasing the
218    ///   file size so reads beyond the new EOF cannot observe stale cached
219    ///   pages.
220    ///
221    /// Accordingly, `old_file_size` must be the pre-resize file size captured
222    /// inside that resize critical section.
223    ///
224    /// # Examples
225    ///
226    /// ```rust
227    /// use ostd::mm::PAGE_SIZE;
228    ///
229    /// use crate::vm::page_cache::PageCache;
230    ///
231    /// let mut page_cache = PageCache::new_anon(0).unwrap();
232    ///
233    /// // Extend: publish the new file size first, then grow the page cache
234    /// // with the previous file size.
235    /// let mut file_size = PAGE_SIZE + 123;
236    /// page_cache.resize(file_size, 0).unwrap();
237    /// assert_eq!(page_cache.size(), 2 * PAGE_SIZE);
238    ///
239    /// // Truncate: shrink the page cache first, while passing the old file
240    /// // size captured in the same critical section.
241    /// let old_file_size = file_size;
242    /// file_size = 512;
243    /// page_cache.resize(file_size, old_file_size).unwrap();
244    /// assert_eq!(page_cache.size(), PAGE_SIZE);
245    /// ```
246    pub(crate) fn resize(&mut self, new_file_size: usize, old_file_size: usize) -> Result<()> {
247        let vmo = &self.0;
248        assert!(vmo.flags.contains(VmoFlags::RESIZABLE));
249
250        if new_file_size < old_file_size && !new_file_size.is_multiple_of(PAGE_SIZE) {
251            let fill_zero_end = old_file_size.min(new_file_size.align_up(PAGE_SIZE));
252            self.fill_zeros(new_file_size..fill_zero_end)?;
253        } else if new_file_size > old_file_size && !old_file_size.is_multiple_of(PAGE_SIZE) {
254            let fill_zero_end = new_file_size.min(old_file_size.align_up(PAGE_SIZE));
255            self.fill_zeros(old_file_size..fill_zero_end)?;
256        }
257
258        let rmap = if new_file_size < old_file_size {
259            Some(vmo.rmap.lock())
260        } else {
261            None
262        };
263
264        let new_cache_size = new_file_size.align_up(PAGE_SIZE);
265        let locked_pages = vmo.pages.lock();
266        let old_cache_size = vmo.size();
267        if new_cache_size == old_cache_size {
268            return Ok(());
269        }
270
271        vmo.size.store(new_cache_size, Ordering::Release);
272
273        if let Some(locked_rmap) = rmap {
274            let decommit_range = new_cache_size..old_cache_size;
275            if let Some(backed_vmo) = vmo.as_backed_vmo() {
276                backed_vmo.decommit_pages(locked_rmap, locked_pages, &decommit_range)?;
277            } else {
278                vmo.decommit_anon_pages(locked_rmap, locked_pages, decommit_range)?;
279            }
280        }
281
282        Ok(())
283    }

285    /// Flushes dirty pages in the specified range to the backend storage.
286    ///
287    /// This walks the current cache contents, submits writeback for pages that
288    /// are dirty when this pass reaches them, and waits for the submitted I/O
289    /// to complete.
290    ///
291    /// Filesystems that need `fsync`-like guarantees must still exclude
292    /// concurrent writers or repeat the operation until their own ordering
293    /// requirements are met.
294    ///
295    /// If the given range exceeds the current size of the page cache, only the pages within
296    /// the valid range will be flushed.
297    pub(crate) fn flush_range(&self, range: Range<usize>) -> Result<()> {
298        let Some(vmo) = self.0.as_backed_vmo() else {
299            return Ok(());
300        };
301
302        vmo.flush_dirty_pages(&range)
303    }
304
305    /// Evicts clean pages within the specified range from the page cache.
306    ///
307    /// Only pages in the `UpToDate` state are removed. Dirty and uninitialized
308    /// pages are left in place. This is useful for invalidating cached data that
309    /// is no longer needed and can be re-read from the backend if necessary
310    /// (e.g., before direct I/O operations).
311    #[cfg_attr(not(ktest), expect(dead_code))]
312    pub(crate) fn evict_range(&self, range: Range<usize>) -> Result<()> {
313        let Some(vmo) = self.0.as_backed_vmo() else {
314            return Ok(());
315        };
316
317        vmo.evict_up_to_date_pages(&range)
318    }
319
320    /// Flushes dirty pages and then evicts clean pages in the specified range.
321    ///
322    /// This is the standard preparation step before issuing direct I/O that must
323    /// bypass the page cache. It uses the same locking requirements as
324    /// [`PageCache::flush_range`] and [`PageCache::evict_range`].
325    pub(crate) fn invalidate_range(&self, range: Range<usize>) -> Result<()> {
326        let Some(vmo) = self.0.as_backed_vmo() else {
327            return Ok(());
328        };
329
330        vmo.flush_dirty_pages(&range)?;
331        vmo.evict_up_to_date_pages(&range)
332    }
333
334    /// Fills the specified range of the page cache with zeros.
335    ///
336    /// Callers must hold the filesystem-level lock that serializes operations in
337    /// the target range.
338    pub(crate) fn fill_zeros(&self, range: Range<usize>) -> Result<()> {
339        self.0.fill_zeros(range)
340    }

358/// A storage backend for a backed [`PageCache`].
359///
360/// This trait is the high-level contract used by the page-cache layer to load
361/// page contents from storage and write dirty contents back. A successful read
362/// makes the requested page usable by readers; a successful write makes the
363/// page's current contents durable in the backend.
364///
365/// Direct implementations are useful for storage that does not naturally expose
366/// block-device BIOs, such as network filesystems. Filesystems backed by block
367/// devices usually implement [`BlockAsPageCacheBackend`] instead.
368pub(crate) trait PageCacheBackend: Sync + Send {
369    /// Reads a page from the backend asynchronously.
370    ///
371    /// The caller may try to pass an index that exceeds the size of the
372    /// underlying backend (e.g., the file size). This can occur if file
373    /// truncation and a page fault occur at the same time. If this happens,
374    /// this method should fail with `EINVAL`.
375    fn read_page_async(
376        &self,
377        idx: usize,
378        locked_page: LockedCachePage,
379        io_batch: &mut IoBatch,
380    ) -> Result<()>;
381
382    /// Writes a page to the backend asynchronously.
383    ///
384    /// If the caller tries to pass an index that exceeds the size of the
385    /// underlying backend (e.g., the file size), this method should fail with
386    /// `EINVAL`. Note that this cannot happen until we support concurrent file
387    /// truncation and page writeback.
388    //
389    // TODO: Revise this behavior once file truncation and page writeback can
390    // happen concurrently.
391    fn write_page_async(
392        &self,
393        idx: usize,
394        locked_page: LockedCachePage,
395        io_batch: &mut IoBatch,
396    ) -> Result<()>;
397}

399impl dyn PageCacheBackend {
400    /// Reads a page from the backend synchronously.
401    pub(crate) fn read_page(&self, idx: usize, page: LockedCachePage) -> Result<()> {
402        let mut io_batch = IoBatch::with_capacity(1);
403        self.read_page_async(idx, page, &mut io_batch)?;
404        io_batch.wait_all()?;
405        Ok(())
406    }
407}

409/// A block-I/O object that can serve as a [`PageCacheBackend`].
410///
411/// This trait is a convenience layer for filesystems whose cached file data is
412/// served by block I/O. Implementors submit the supplied [`BioSegment`] for the
413/// page at the requested index.
414///
415/// The blanket [`PageCacheBackend`] implementation adapts this trait to the
416/// generic page-cache backend contract.
417///
418/// The `complete_fn` passed to submit methods may run from interrupt context,
419/// so implementations must not allocate, take blocking locks, or hold a lock
420/// that a waiter on the page wait queue may already hold.
421//
422// TODO: This trait should provide interfaces for reading or writing multiple
423// pages in a single BIO to improve efficiency for sequential I/O.
424pub(crate) trait BlockAsPageCacheBackend: Sync + Send {
425    /// Submits read I/O for the page at `idx`.
426    ///
427    /// `bio_segment` identifies the page memory that must receive the data.
428    /// Implementations must attach `complete_fn` to the underlying
429    /// asynchronous I/O so the page-cache layer can mark successful
430    /// reads up to date and release the page lock.
431    ///
432    /// If the page only contains zeros, implementations may call `complete_fn`
433    /// with [`BioStatus::Zeros`], skip I/O, and leave `bio_segment` unfilled.
434    ///
435    /// Implementations should fail with `EINVAL` for an out-of-bounds `idx`.
436    /// See also [`PageCacheBackend::read_page_async`].
437    fn submit_read_bio(
438        &self,
439        idx: usize,
440        bio_segment: BioSegment,
441        complete_fn: BioCompleteFn,
442        io_batch: &mut IoBatch,
443    ) -> Result<()>;
444
445    /// Submits write I/O for the page at `idx`.
446    ///
447    /// `bio_segment` contains the stable page snapshot that must be written.
448    /// Implementations must attach `complete_fn` to the underlying
449    /// asynchronous I/O so the page-cache layer can finish writeback
450    /// bookkeeping and report failures.
451    ///
452    /// Implementations should fail with `EINVAL` for an out-of-bounds `idx`.
453    /// See also [`PageCacheBackend::write_page_async`].
454    fn submit_write_bio(
455        &self,
456        idx: usize,
457        bio_segment: BioSegment,
458        complete_fn: BioCompleteFn,
459        io_batch: &mut IoBatch,
460    ) -> Result<()>;
461}
462
463impl<T: BlockAsPageCacheBackend> PageCacheBackend for T {
464    fn read_page_async(
465        &self,
466        idx: usize,
467        locked_page: LockedCachePage,
468        io_batch: &mut IoBatch,
469    ) -> Result<()> {
470        let bio_segment = BioSegment::new_from_segment(
471            Segment::from(locked_page.deref().clone()).into(),
472            BioDirection::FromDevice,
473        );
474
475        let complete_fn: BioCompleteFn = Box::new(move |status| {
476            if status == BioStatus::Zeros {
477                locked_page.fill_zeros(0, PAGE_SIZE).unwrap();
478                locked_page.set_up_to_date();
479            } else if status == BioStatus::Complete {
480                locked_page.set_up_to_date();
481            }
482            // The page lock is released when `locked_page` (LockedCachePage) is dropped here.
483        });
484
485        self.submit_read_bio(idx, bio_segment, complete_fn, io_batch)
486    }
487
488    fn write_page_async(
489        &self,
490        idx: usize,
491        locked_page: LockedCachePage,
492        io_batch: &mut IoBatch,
493    ) -> Result<()> {
494        locked_page.wait_until_finish_writing_back();
495
496        let bio_segment = BioSegment::alloc(1, BioDirection::ToDevice);
497        bio_segment
498            .writer()
499            .unwrap()
500            .write(&mut locked_page.reader());
501
502        locked_page.set_writing_back();
503        locked_page.set_up_to_date();
504
505        let page = locked_page.unlock();
506        let submit_page = page.clone();
507
508        let complete_fn: BioCompleteFn = Box::new(move |status| {
509            submit_page.clear_writing_back();
510            if status != BioStatus::Complete {
511                // TODO: Record the writeback error (e.g., EIO) in the VMO
512                // (or the corresponding inode) so that a subsequent sync syscall
513                // can detect and report it to userspace.
514                //
515                // Following Linux's design, we intentionally do **not** re-dirty the
516                // page here. Re-dirtying would cause the writeback mechanism to retry
517                // the I/O indefinitely, which could stall the entire system if the
518                // underlying device has a persistent hardware fault. Instead, the page
519                // is left clean and the data is considered lost.
520                ostd::error!(
521                    "writeback I/O failed for page index {idx} with status {status:?}; data may be lost"
522                );
523            }
524        });
525
526        let res = self.submit_write_bio(idx, bio_segment, complete_fn, io_batch);
527        if res.is_err() {
528            // If submission fails, re-dirty the page so the next writeback can
529            // retry the data that never reached the device queue.
530            let locked_page = page.lock();
531            locked_page.set_dirty();
532            locked_page.clear_writing_back();
533        }
534
535        res
536    }
